## What is a workspace?

EAIS operates on a **workspace** basis. A workspace is a folder that contains the model file (`.onnx` or `.tflite`) to be converted, and the folder name and the model file name must match. When you run `eais init`, a `<model_name>.yaml` file and a `Config/` folder are created inside the workspace, and subsequent CLI commands store artifacts such as conversion, compile, and profiling results based on this workspace. Each model has a single workspace, and artifacts produced by each CLI command are stored under the workspace folder.

> For workspace preparation rules, the full list of yaml files under `Config/`, and the role of each file, refer to [EAIS_User_Guide.md → §2 Workspace Structure](./EAIS_User_Guide.md#2-workspace-structure).

## 1. Changes compared to SDK 2.5

### 1-1. yaml configuration file structure has been redesigned — existing workspaces must be re-initialized

> [!CAUTION]
> In SDK 3.0, the composition and content of `<model_name>.yaml` and the yaml files under `Config/` differ from SDK 2.5.
> If yaml files generated by `eais init` in SDK 2.5 exist in the workspace, conflicts may occur, so **be sure to delete them and run `eais init` again.**
> If you use files generated in SDK 2.5 as-is, parameters may not be recognized or errors may occur.

In particular, the structure of the `converter` section in `<model_name>.yaml` has been completely redesigned.

**SDK 2.5 structure (no longer supported)**
```yaml
converter:
  mode: legacy
  quantize:
    precision_weight: 8
    precision_activation: 8
  specify:
    input_dtype: float32
    output_dtype: float32
    graph_opt: common
    tv_input: Config/DATA/database.h5
  optimizer:
    ...
  runtime:
    ...
```

**SDK 3.0 structure**
```yaml
converter:
  precision: A8W8
  input_dtype: float32
  output_dtype: float32
  graph_opt: common
  # Advanced options are configured in Config/conversion_expert.yaml
```

The key changes are as follows.

| SDK 2.5 | SDK 3.0 | Description |
|---|---|---|
| `mode: legacy` | `mode: pro` | pro mode is used as the default mode |
| `quantize.precision_weight` + `precision_activation` | `precision: A8W8` | The two values are consolidated into a single profile |
| `specify.input_dtype` | `input_dtype` | Nested structure → simplified to flat structure |
| `specify.output_dtype` | `output_dtype` | Same |
| `specify.graph_opt` | `graph_opt` | Same |
| `specify.tv_input` | Set automatically | The generation artifact path is referenced automatically |
| `optimizer.*`, `runtime.*` | Moved to `Config/conversion_expert.yaml` | Advanced parameters are separated |

> [!IMPORTANT]
> Parameters are split into two files depending on the usage level.
>
> - **`<model_name>.yaml`**: Parameters that are typically adjusted during model conversion (`precision`, `calibration_method`, `input_dtype`, etc.)
> - **`Config/conversion_expert.yaml`**: Advanced parameters related to optimization, quantization, etc. Automatically generated on `eais init` and modified only in special cases.
>

### 1-2. Calibration data format has been changed from `.h5` to `.npy`, so data must be regenerated

In SDK 2.5, `eais generation` produced `.h5` files, but starting with SDK 3.0, it has been changed to `.npy` files.
> [!WARNING]
> Existing `.h5` files cannot be used with `eais conversion` in SDK 3.0. You must re-run `eais generation` in the SDK 3.0 container.

**Output structure in SDK 3.0**
```
Config/DATA/
├── database.txt
├── database.json
└── input_data/
    ├── input_folder_mapping.json
    └── <input name>/
        ├── database_0000.npy
        ├── database_0001.npy
        └── ...
```

#### Changes in `Config/DATA/dbgen_spec.yaml`

The `raw_shape` and `raw_order` fields used in SDK 2.5 have been consolidated into `shape` and `order` in SDK 3.0.

> For a full description of the `dbgen_spec.yaml` fields, multi-input/random data examples, path relative-path interpretation rules, and other authoring guidance, refer to [EAIS_User_Guide.md → Step 2 → How to write dbgen_spec.yaml](./EAIS_User_Guide.md#how-to-write-dbgen_specyaml).

## 2. Newly added features



### 2-1. Check the list of configurable parameters with `eais conversion --help`

Starting with SDK 3.0, running `eais conversion --help` prints the list of parameters defined in the `converter` section of `<model_name>.yaml` along with their descriptions.

```bash
eais conversion --help
```

Example output (partial):
```
[GENERAL]
--mode  <STR>  [Default: 'pro']  {legacy, pro, eht, elt, gen-ai-eht, gen-ai-elt, gen-ai}

[EHT MIXED PRECISION]
--mixed_precision_type    <STR>   [Default: 'manual']  {manual, auto}
--mixed_precision_layers  <DICT>  [Default: '{}']
--mixed_precision_ops     <DICT>  [Default: '{}']

[EHT CALIBRATION]
--calibration_args  <DICT>  [Default: '{"seed": 42, "samples": 1}']

[EHT BLOCKWISE QUANTIZATION]
--enable_blockwise_quantization  <BOOL>  [Default: False]
--blockwise_block_size           <INT>   [Default: 64]
--blockwise_bitwidth             <INT>   [Default: 4]
...
```

The full output is organized into 12 sections: GENERAL / EHT CONVERTER / EHT MIXED PRECISION / EHT CALIBRATION / EHT BLOCKWISE QUANTIZATION / EHT AUTOMATIC MIXED PRECISION / EHT ADVANCED ALGORITHMS / EHT WEIGHT HANDLING / EHT DEBUGGING AND OTHERS / EHT GEN AI OPTIMIZE ARGS / ELT / ELT HWOP SPECIFIER, and so on.

You can check parameter names, allowed values, and defaults directly from `--help` without opening the yaml file, and you can also override parameters from the CLI without modifying the yaml.

```bash
eais conversion --w <workspace> --mode pro --mixed_precision_type auto
```

> For default values and meanings of each parameter in `<model_name>.yaml` (`precision`, `calibration_method`, `graph_opt`, etc.), refer to [EAIS_User_Guide.md → `<model_name>.yaml` Parameter Guide](./EAIS_User_Guide.md#model_nameyaml-parameter-guide).

### 2-2. `Converter_result/` folder structure changes

The `Converter_result/` folder structure created in the workspace after running `eais conversion` has been changed.
In SDK 2.5, artifacts from each conversion stage were scattered across separate folders (`cnnx/`, `optimized/`, `quantized/`, `quantized_mp/`), but in SDK 3.0 they have been consolidated into numbered folders that follow the pipeline order — `0_onnx_to_cnnx/` → `1_optimize/` → `2_mixed_precision_quantization/` — making the stage flow clearer.

**SDK 2.5 structure**
```
Converter_result/
├── cnnx/                    ← Converter artifacts
│   ├── output.onnx
│   └── output.encodings
├── optimized/               ← Optimizer artifacts
│   ├── output.onnx
│   ├── output.encodings
│   └── 4dim/
├── quantized/               ← Quantizer artifacts
│   ├── <model>.onnx
│   └── <model>.encodings
├── quantized_mp/            ← Mixed-precision quantizer artifacts
│   ├── output.onnx
│   └── output.encodings
├── convert/
├── log/
├── processed_cnnx/
├── quantizer_input_data_npy/
├── recipe/
├── simulator_input_data_npy/
├── HW_<model>_new_snc_<version>.snc
├── HWQuant_<model>_new_snc.snc
├── OutportReshape_<model>_new_snc.snc
├── QAT_<model>_new_snc.snc
├── ennpartitioner_cmd.txt
├── ennquantizer_cmd.txt
└── org_vs_hwsnc_snr.txt
```

**SDK 3.0 structure**
```
Converter_result/
├── 0_onnx_to_cnnx/                   ← Converter artifacts
│   ├── output.onnx
│   ├── output.encodings
│   └── validation/                   ← ModelValidator results (see 2-3)
├── 1_optimize/                       ← Optimizer artifacts
│   ├── output.onnx
│   ├── output.encodings
│   ├── output_mapping_table.json
│   ├── 4dim/
│   └── validation/
├── 2_mixed_precision_quantization/   ← Mixed-precision quantizer artifacts
│   ├── output.onnx
│   ├── output.encodings
│   └── validation/
├── convert/
├── NPU_<model>/
├── recipe/
├── HW_output_new_snc_<version>.snc
├── HWQuant_output_new_snc.snc
├── OutportReshape_output_new_snc.snc
├── QAT_output_new_snc.snc
├── ennpartitioner_cmd.txt
├── ennquantizer_cmd.txt
└── org_vs_hwsnc_snr.txt
```

Key changes:

| SDK 2.5 | SDK 3.0 | Description |
|---|---|---|
| `cnnx/` | `0_onnx_to_cnnx/` | Numeric prefixes added to reflect the pipeline order |
| `optimized/` | `1_optimize/` | Same |
| `quantized_mp/` | `2_mixed_precision_quantization/` | Same |
| `quantized/` | Removed | Consolidated into the mixed-precision quantizer in SDK 3.0 |
| `log/`, `.log/`, `processed_cnnx/`, `quantizer_input_data_npy/`, `simulator_input_data_npy/` | Removed | Internal temporary artifacts cleaned up |

### 2-3. Per-stage validity check (ModelValidator) added

ModelValidator is automatically executed immediately after each stage (Converter, Optimizer, Quantizer) of the `eais conversion` pipeline completes. The inspection results (`report.html`, `validation_report.json`) are stored under `validation/model_validation_results/` inside each stage's result folder.

- **After Converter / Optimizer**: 4 ONNX checks (dynamic dimensions, ONNX Runtime executability, opset version, whether `Einsum` is included)
- **After Quantizer**: the 4 ONNX checks above + 14 CNNX quantization encodings checks = 18 checks in total

If all checks pass, `results` in `validation_report.json` is an empty object `{}`; if any fail, the corresponding validator name and `fail_list` (node name, error code, cause) are recorded.

> For the full list of per-validator inspection contents, the structure of `validation_report.json` with failure examples, and how to use `report.html`, refer to [EAIS_User_Guide.md → ModelValidator](./EAIS_User_Guide.md#modelvalidator--validity-check-of-the-converted-model).

### 2-4. `--eht` / `--elt` options added to select the conversion stage

The `--eht` and `--elt` options have been added to `eais conversion`, allowing you to run only a portion of the conversion pipeline. If no option is specified, the entire pipeline is executed.

```bash
eais conversion --w <workspace>         # Full run (recommended)
eais conversion --w <workspace> --eht   # Only hardware-independent stages (CNNX generation)
eais conversion --w <workspace> --elt   # Only hardware-dependent stages (Specifier)
```

- `--eht`: Generates up to the EHT result — the quantized CNNX (`.onnx` + `.encodings`).
- `--elt`: Reuses an already completed EHT result to generate only the device-specific SNC (e.g., reconvert for a different SoC target).

> For each option's execution range, usage timing, and common errors (such as `IndexError` when running `--elt` alone), refer to [EAIS_User_Guide.md → Step 3 conversion](./EAIS_User_Guide.md#step-3-conversion--model-conversion).

### 2-6. `eais debug` added to verify conversion accuracy and model graph stage by stage

`eais debug` is a new command that analyzes the outputs of `eais conversion`. It allows you to check accuracy loss at each stage of the conversion process, visualize the model graph in a browser, and even perform diffs between two models — all in a single command.

You select what to run with the `--mode` option.

| `--mode` | Description |
|---|---|
| `accuracy` (default) | Computes accuracy metrics (SNR, PSNR, COSSIM, etc.) between the outputs of each conversion module and saves them to `accuracy_comparison.xlsx` / CSV |
| `visualize` | View the model graph, node/tensor properties, activation distributions, and accuracy results in a browser. Supports diff comparison of two models and preloading accuracy results |
| `all` | Runs `--mode accuracy` first, then `--mode visualize` in order |

```bash
# Accuracy validation (default)
eais debug --w ./hrnet_pose

# Visualize the final SNC model
eais debug --w ./hrnet_pose --mode visualize \
  --base_model_path ./Converter_result/HW_output_new_snc_9.7.9.30.snc
```

When you run `--mode visualize` / `--mode all`, you can check the following in the browser (default `http://127.0.0.1:40090`):

- **Graph view** — Model topology, node/edge/tensor properties, and activation distributions (histograms)
- **Accuracy view** — Pipeline Flow / Dashboard / Layer-wise Analysis / Summary Report
- **Diff mode** — Compare two models side by side in left/right panes
- **SNC edit & Export** — Edit SNC attributes and quantization metadata, and re-export the SNC

## 3. Default value changes

---

### 3-1. Default target device has been changed to Gen-9

The default target device in `<model_name>.yaml` generated after `eais init` has been changed from `Gen-8` to `Gen-9`.

```yaml
general:
  device: Gen-9   # In SDK 2.5, Gen-8 was the default
```

> [!NOTE]
> **If you are working with a Gen-8 target:** after `eais init`, manually change the value to `device: Gen-8`. For the supported SoC mapping per Gen-2 to Gen-9, refer to [EAIS_User_Guide.md → general section](./EAIS_User_Guide.md#general-section).

---

### 3-2. The `simulator` section has been removed from `<model_name>.yaml`

The `simulator` section that was included in `<model_name>.yaml` in SDK 2.5 has been removed.
If you need simulator-related parameters, refer to `Config/conversion_expert.yaml`.
